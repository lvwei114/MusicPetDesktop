# MusicFree 切歌断连定位（2026-10-20）

## 测试方式

运行独立诊断工具，使用 src/media.cpp 的副本，仅插入日志。未修改生产源码、未重编译或替换 MusicPet.exe。用户手动播放、切歌并确认已复现。工具选择首个正在播放的会话并固定选择；本次只有 MusicFree.exe 一个媒体来源。测试程序不发送播放控制命令。

日志时间为 GetTickCount64 单调毫秒，日志包含本机曲目名称。原始记录：media-switch-trace.log。

| --- | --- | --- | --- |
| 1 | 467123078 / 467123078 | 467123750 | 672 ms |
| 2 | 467125125 / 467125125 | 467125796 | 671 ms |
| 3 | 467144875 / 467144890 | 467145562 | 672 ms |

每次过程均为 SESSION_COUNT 1 → 0 → 1；MediaWatcher 会话标识依次 MusicFree.exe#1 → #2 → #3 → #4，表示旧会话从已知集合消失后，重新发现会话并生成新编号。该编号本身不单独证明底层 COM 身份改变。

日志没有 ERROR 记录。188 次成功歌名查询耗时 0～16 ms，平均约 3.4 ms（日志精度及写入开销会影响结果）。读取日志后，MusicPet 和 MusicFree 进程均仍在运行并响应。

## 定位

1. MusicFree 切歌时确实出现 GSMTC 会话列表短暂无会话的过渡，而非播放器进程退出。
2. src/media.cpp 的 Tick 在没有 chosen 时立即清空标题、时间轴并发布 valid=false（约第 162～167 行）。没有过渡状态或短暂断连缓冲。
3. Run 在本轮结束后等待 650 ms（约第 174 行），导致新会话需下一轮才能发现。本次可观察到的无效状态持续约 0.67 秒；不能据此断言系统会话实际消失了同样长时间。
4. main.cpp 在 WM_APP_MEDIA_UPDATE 收到空快照后立即更新 UI，替换歌名、隐藏进度并停发音符。固定选择仍被保留，唯一同源会话回来后重绑成功。

因此本次根因是：播放器会话过渡被桌宠立即当作断连处理，650 ms 轮询进一步延迟恢复。本次没有证据表明元数据等待超时引发断连。

## 验证边界

日志来自使用相同媒体算法的独立进程，并非对运行中主程序注入日志；主程序的实时 UI 消息时刻未记录。没有测量按钮点击到新曲实际播放的总延迟。其他客户端、多媒体来源、极慢查询的表现不在本次结论内。

## 后续修复方向（未实施）

区分短暂会话过渡与真正关闭；保留选择和过渡展示状态；用 GSMTC 会话/曲目变化事件唤醒查询并保留轮询兜底；检验过渡期间控制命令的旧会话目标处理。过渡缓存期间不能继续向已失效会话发命令，也不能把旧曲进度展示为新曲进度。
